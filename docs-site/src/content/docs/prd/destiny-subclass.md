# Subclass — Destiny object

> [!abstract] One-liner
> Class + element/tree container for aspects, fragments, and abilities.

Hub: [Destiny Objects](/prd/destiny-objects/) · Children: [Destiny Aspect](/prd/destiny-aspect/) · [Destiny Fragment](/prd/destiny-fragment/) · [Destiny Ability](/prd/destiny-ability/)

## 1. Definition (Destiny / DIM)

A **subclass** is the Guardian’s combat style for one **class** and one **element/tree**:

| Trees |
| --- |
| Solar, Arc, Void, Stasis, Strand, Prismatic |

It is the **container** for:

| Child object | Role |
| --- | --- |
| [Destiny Aspect](/prd/destiny-aspect/) | Major tree choices; grant fragment capacity (see DO-ASP-*) |
| [Destiny Fragment](/prd/destiny-fragment/) | Modular plugs under aspect capacity (see DO-FRG-*) |
| [Destiny Ability](/prd/destiny-ability/) | Super, melee, grenade, class ability, movement (see DO-ABL-*) |

DIM shows this as an equipped subclass kit (icons for aspects, fragments, abilities).

### Product split (critical)

| Concern | Owner |
| --- | --- |
| **Class** | [Domain Build](/prd/domain-build/) — fixed after create |
| **Element / tree** | [Domain Build](/prd/domain-build/) — shared; change = confirm or fork, then wipe Subclass to empty legal baseline |
| **Aspects, fragments, abilities** | [Domain Variant](/prd/domain-variant/) — **Subclass area**; may differ per variant |
| **Build-pinned Super** | [Domain Build](/prd/domain-build/) identity when pinned |
| **Exotic-required abilities** | Auto-propose pins; mismatch hard (DBR-SUB-005) |

### Create / tree-change baseline

After create or tree change (confirm/fork): Subclass area is an **empty legal baseline** for that tree (BR-BLD-040a).  
User fills aspects, fragments, and abilities before default is composition-complete.

## 5. Hard vs soft

### Hard

| Rule | Where |
| --- | --- |
| Tree shared across all variants | Build |
| Illegal kit (capacity, invalid combo) cannot save | Variant |
| Exotic-required ability mismatch blocks save | Variant / Build pins |
| Default must have legal complete kit for full loadout | Variant §3.2 |
| Class cannot change after create | Build |

### Soft

| Topic | Rule |
| --- | --- |
| Weapon element vs subclass element | Soft / synergy-based |
| Prismatic | Same rules as other trees (DBR-SUB-002) |
| Weak synergy coverage | Soft on non-default |

### Object rules

| ID | Rule |
| --- | --- |
| DO-SUB-001 | Subclass is the container; aspects, fragments, and abilities are child objects. |
| DO-SUB-002 | Variant **Subclass** area is the only compose surface for kit picks (not General/Weapons/Armor). |
| DO-SUB-003 | Tree is **read-only** in Variant; change tree on Build with confirm/fork. |
| DO-SUB-004 | Presentation is icon-first; capacity and empty slots visible. |
| DO-SUB-005 | Illegal options are not selectable when known; API still rejects illegal kits. |
| DO-SUB-006 | Build-pinned Super and exotic-required abilities are visually distinct (locked/badge). |
| DO-SUB-007 | Hashes never primary UI (footer addendum only). |
| DO-SUB-008 | After tree change, kit is wiped to empty legal baseline; user rebuilds. |
| DO-SUB-009 | **Default complete kit** requires: legal **aspects** and **fragments at capacity**, plus **Super**, **melee**, and **grenade** selected. |
| DO-SUB-010 | **Class ability** and **movement** are always shown and editable in Subclass area; they are **not** required for default composition complete unless an exotic ability requirement forces them. |
| DO-SUB-011 | Build library / identity chrome shows a **full mini kit strip** (element + aspects + fragments + five ability icons), not element-only. |
