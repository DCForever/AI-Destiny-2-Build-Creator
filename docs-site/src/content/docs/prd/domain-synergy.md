## Glossary (fixed terms)

| Term | Meaning |
| --- | --- |
| **Library Synergy** | A saved record: designation + description + linked Objects. This product. |
| **Designation** | `type` + optional `subType` (e.g. Verb + Devour). |
| **Synergy Type designation** | Designation only, on a Build or Set. No Object required. |
| **Object / link / evidence** | A manifest-backed target linked to a library Synergy. Kind enum in §6.4. |

## 1. Definition

A **library Synergy** is a user-owned play-pattern record.  
It has a **designation** (`type` + optional `subType`).  
It has optional **description**.  
It has zero or more **linked Objects** (evidence or required).

A **Synergy Type designation** on a Build or Set is designation only.  
A library Synergy is not required for a designation to be valid.

## 2. Why it exists

Builds are **intent-first**.  
Players name play-patterns, then attach gear evidence.  
The system bridges Build (and Set) designations to library Synergies.  
That drives coverage, soft guidance, and suggestions.  
A deep library is a readiness bar.  
A deep library is not a hard gate to start compose (`DBR-PUR-004`).

## 3. Shape

| Aspect | Rule summary |
| --- | --- |
| Ownership | Private per user. |
| Designation | Fixed `type` enum + `subType` when required. **Fixed after create.** |
| Name | Designation string (e.g. Verb: Jolt). Unique per user. |
| Description | Optional free text (notes). |
| Editable after create | Description and links only. |
| Links | Evidence by default. Author may mark required. |
| Multi-required | AND — all required links must pass. |
| Required hard check | **Default variant** only. Other variants: soft. |
| Bridge | Designations on Build and Set match library Synergies by Type. |
| Verb → element | System may imply element for bridge when known. Explicit element wins. |
| LLM | Manual propose-for-confirm only. Never auto-save. |
| Lifecycle | One create/edit/delete experience for every entry point. |

## 3a. Constraints (hard vs soft)

### Hard on library Synergy save

| Constraint | Rule |
| --- | --- |
| **Designation required** | Create requires a valid creatable `type` and a `subType` when the type family requires one (§6.3). |
| **Designation unique** | At most one library Synergy per user per type+subType. |
| **Designation immutable** | Edit must not change `type` or `subType`. |
| **No personal types (v1)** | User cannot invent new type keys. Use the product enum only. |
| **Link kind enum** | Link kind is a fixed list, not free text. |
| **Manifest target** | Each link target must validate for its kind. Invalid → `INVALID_SYNERGY_LINK`. |
| **No duplicate target** | One library Synergy has each evidence target at most once. |
| **LLM not silent** | LLM output never becomes a library Synergy without user confirm. |

### Soft only (library)

| Topic | Rule |
| --- | --- |
| Zero evidence links | Library Synergy may save with no links. Soft nudge allowed. **Decided.** |
| LLM proposals | Soft until user confirms. |
| Library depth | ≥10 synergies is a readiness bar, not a compose gate. |

### Deferred consumers (not library law)

- Soft coverage on non-default variants
- Soft element match on compose
- Required set-bonus links (SETB)

See §6.5.

| Topic | Owner |

## 4. In scope / out of scope

**In**

- Library Synergy CRUD with one lifecycle
- Designation create; immutable after create
- Evidence and required links; multi-required AND
- Link kinds: full enum in §6.4 (gear, perks, armor set bonuses, subclass kit pieces, armor mods, artifact)
- Fixed type enum and subType rules (§6.3)
- Bridge match key from designations (Build consumer rules deferred)
- Reverse lookup: all library Synergies for a target
- Manual LLM propose-for-confirm
- In-flow create during compose via shared lifecycle

**Out**

- Free-text “vibes” as identity instead of designation
- Editing type/subtype after create
- Requiring a library hit to save a Build or to designate a Type
- Auto-apply LLM without confirm
- Concept tags as synergy identity
- Auto LLM on every edit
- Personal custom type keys in v1
- Promote personal → global vocabulary in v1

## 5. Success

| Signal | Pass when |
| --- | --- |
| Curate | User creates library Synergies with valid links |
| Immutable designation | Edit cannot change type/subtype |
| Unique designation | Second row with same type+subType is rejected |
| Required links | *(Draft)* Default variant hard-checks required links |
| LLM | Propose only; confirm required; no new type keys without product enum |
| In-flow | Create works during compose via same lifecycle |
| Bridge | Designations match library Synergies for coverage |
| Library bar | Supports readiness bar with Sets (`DAC-P1-009`) |

### 6.4 Links (Objects)

**This section is the product SSoT for linkable object kinds.**  
Code should match when implemented (`synergyLinkKindSchema` in `src/lib/synergies/schemas.ts`). Product is ahead of code until re-sync.

#### Linkable kinds (v1)

| Kind key | Label | What it points at |
| --- | --- | --- |
| `weapon` | Weapon | Catalog weapon item |
| `weapon_perk` | Weapon perk | Legendary perk **or** exotic weapon trait plug (see DBR-SYN-014) |
| `origin_trait` | Origin trait | Weapon origin trait |
| `armor_set_bonus` | Armor set bonus | Bonus **family** + **target tier** (2 or 4). Required when count ≥ tier. Not an Armor Set constraint. See [Destiny Armor Set Bonus](/prd/destiny-armor-set-bonus/) DO-ASB-011, 016–019. |
| `exotic_armor` | Exotic armor | **Classic:** item hash. **Class item:** perk config only (not shell). See [Destiny Exotic Armor](/prd/destiny-exotic-armor/) DO-EXO-012 / 012a. |
| `aspect` | Aspect | Subclass aspect |
| `fragment` | Fragment | Subclass fragment |
| `armor_mod` | Armor mod | Armor mod plug |
| `melee` | Melee ability | Subclass melee ability (not the Melee **type** designation) |
| `grenade` | Grenade ability | Subclass grenade ability |
| `super` | Super ability | Subclass Super ability |
| `artifact_perk` | Artifact perk | Seasonal artifact perk |

Kind keys `melee` / `grenade` / `super` here are **link kinds** (abilities).  
They are not the same as designation types `melee` / `grenade` / `super` (§6.3). Context is always “link kind” vs “designation type.”

#### Link rules

| ID | Rule |
| --- | --- |
| DBR-SYN-007 | Links are evidence by default. Authors may mark a link required. |
| DBR-SYN-008 | Required may apply to any link kind in the table above. |

| BR-SYN-002 | A library Synergy may only link targets whose kind is in the linkable kinds table. |
| BR-SYN-007 | Link kinds are that fixed enumeration. Free-form text is not a kind. |
| BR-SYN-005 | Each link is validated against manifest (or product) data for its kind. Invalid → `INVALID_SYNERGY_LINK`. |
| BR-SYN-006 | One library Synergy may link many targets. |
| BR-SYN-008 | One target may link to many library Synergies (many-to-many). |
| BR-SYN-011 | Within one library Synergy, each target appears at most once (same kind + same target identity). |
| BR-SYN-011a | Link search omits targets already on the draft. Save dedupes by kind + target identity. |
| DBR-SYN-014 | Weapon perk evidence includes exotic weapon trait plugs, not only legendary rolls. |
| BR-SYN-012 | Weapon-perk search labels exotic intrinsic/trait vs legendary (or both) when known. |
| BR-SYN-014a | **Perk family match:** for `weapon_perk` coverage and required-link satisfaction, base and enhanced (family variants) of the same trait **count as a match** when family is known. Saved rolls still store the specific plug hash. See [Destiny Weapon Perk](/prd/destiny-weapon-perk/) DO-WPK-013–014. |
| BR-SYN-014b | **`armor_set_bonus` links** store **family + target tier** (2 or 4). Required satisfaction: contributing member count on resolved loadout **≥ target tier** (higher count OK). Tier must exist on that family in data. Independent of Armor Set package constraint. See [Destiny Armor Set Bonus](/prd/destiny-armor-set-bonus/) DO-ASB-016–019. |
| BR-SYN-004 | Reverse lookup: when a production surface shows a linkable entity, it shows library Synergies that link that target. |
| BR-SYN-004a | v1 scope: production library and compose readouts that already show the entity (catalog detail, set item detail, inventory instance detail when exposed). Not every debug screen. |
| BR-SYN-004b | Missing chips on a non-listed surface is polish, not a library save failure. |
| BR-SYN-019 | Ability link kinds (`melee`, `grenade`, `super`) resolve to ability definitions, not to designation type rows. |
| BR-SYN-019a | **v1:** No link kinds for class ability or movement. |
