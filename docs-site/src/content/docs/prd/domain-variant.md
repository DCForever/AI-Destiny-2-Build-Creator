# Variant — domain product description

> [!abstract] One-liner
> A kit slice under a Build with four areas: General, Subclass, Armor + Mods, Weapons. Default must be complete; others may gap.

Catalog: [Products](/prd/products/) · UI: [Area Build](/prd/area-build/) (composer)

| Term | Meaning |
| --- | --- |
| **Variant** | One named kit under a Build |

| **Wishlist** | Desired item/roll without a pinned owned instance |

## 1. Definition

A **Variant** is a kit slice under one [Domain Build](/prd/domain-build/).  
It always has **four distinct areas**:

1. **General**  
2. **Subclass**  
3. **Armor + Mods Sets**  
4. **Weapons Set**  

Together these areas hold set attachments, slot overrides, rolls and pins, subclass kit (within the shared tree), artifact, fashion, soft targets, and notes.  
The variant does **not** own Build identity fields.  
Exactly one variant is the **default**.

## 2. Why it exists

Players keep one play-pattern identity and many loadouts.  
They change weapons, armor, mods, or activity setup without forking a new Build every time.  
Four fixed areas keep every variant navigable the same way.

## 3. Shape

| Aspect | Rule summary |
| --- | --- |
| Parent | Always one Build |
| Count | One default + zero or more non-default |
| **Areas** | Always **General**, **Subclass**, **Armor + Mods**, **Weapons** |
| Label | User label + optional derived hint (General) |
| Composition | Sets (live default) + slot overrides in Armor/Mods and Weapons |
| Completeness | Default: full combat loadout (by area). Non-default: gaps allowed |
| Three gates | Compose complete → required links (pins) → equip-ready |
| Wishlist | May save under compose rules; required links and equip need pins |
| Artifact / fashion | General; artifact **required** on default (pick + perks filled); fashion optional |
| Soft stats / guidance | Shown across areas; soft only on non-default save |
| Equip / export | Sticky chrome + readiness summary in General |
| Identity edits | Confirm or fork on **Build** — not a silent variant-only change |

### 3.1 Four areas (always present)

Every variant **always** exposes these four areas. The UI must not hide or merge them into a single undivided surface.

| Area | Owns (product) |
| --- | --- |
| **General** | Variant label and notes; artifact pick + **filled perk/config**; fashion (optional); soft stat readout; equip/export **readiness summary**; soft guidance summary. Primary equip/export actions also live in **sticky chrome** outside the four areas |
| **Subclass** | Aspects, fragments, and abilities within the Build’s shared element/tree; respect build-pinned Super and exotic-required ability pins |
| **Armor + Mods Sets** | **Attach** Armor/Mod Sets (separate from create/edit); armor slot overrides and pins; armor exotic exclusivity; set-bonus soft readout |
| **Weapons Set** | **Attach** Weapon Set (and Pair when used); weapon slot overrides and pins; weapon exotic exclusivity |

**Rules**

| BR-VAR-032 | The composer must present all four areas for every variant (default and non-default). |

### 3.1a Set operations in Sets areas (distinct)

In **Armor + Mods Sets** and **Weapons Set** (and Fashion under General when used), Set work is **three separate operations**. The product must not merge them into one overloaded control.

| Operation | What it does | Experience |
| --- | --- | --- |
| **Create Set** | Make a new library Set | Same **Sets lifecycle** as [Area Sets](/prd/area-sets/) / [Domain Set](/prd/domain-set/) (BR-SET-020–026). Prefill type from the area (e.g. Armor, Mod, Weapon). Optional post-create offer to attach — not automatic without user confirm. |
| **Edit Set** | Change an existing library Set | Same **Sets lifecycle** as library edit (fields, validation, save, delete rules). Entry may open the attached Set or a chosen library Set. |
| **Attach Set(s)** | Link library Set(s) to this variant (live/snapshot) | **Separate flow** from create/edit. Attach picker / attach panel only: choose Set(s), mode live|snapshot, replace-by-type, attach rules (BR-ATT-*). No full Set editor chrome. |

| ID | Rule |
| --- | --- |
| BR-VAR-060 | Create Set, Edit Set, and Attach Set(s) are **distinct** operations in variant Sets areas. |
| BR-VAR-061 | Create Set and Edit Set always use the **shared Sets lifecycle** ([Domain Set](/prd/domain-set/) BR-SET-020–026). Same fields, validation, and outcomes as `/sets`. |
| BR-VAR-062 | Attach Set(s) is a **separate** surface or step. It must not embed the full create/edit form. |
| BR-VAR-063 | Attach may list attachable Sets (pass Set save rules), support multi-select where product allows, set live/snapshot, and apply replace-by-type. |
| BR-VAR-064 | The UI must not present a single combined “create or attach” form that mixes library fields with attach mode. Optional: after Create, a **separate** confirm “Attach to this variant?” |
| BR-VAR-065 | Edit of an attached Set opens the Sets lifecycle; it does not change attach mode unless the user uses Attach controls. |
| BR-VAR-066 | Detach / replace attach is part of the **Attach** operation family, not Edit Set. |
| BR-VAR-067 | In-flow Create from a Sets area still uses the shared lifecycle (no lite create chrome). |

### 3.2 Full combat loadout (default — composition complete)

Composition complete is **not** the same as equip-ready. Pins are separate gates (§3.3).

| Area | Default must have |
| --- | --- |
| **Subclass** | Legal kit: aspects **slots filled** (typically 2 when known) + fragments **at capacity**; **Super**, **melee**, **grenade** required; class ability + movement shown (required only if exotic forces). See [Destiny Subclass](/prd/destiny-subclass/) DO-SUB-009–010; [Destiny Aspect](/prd/destiny-aspect/) DO-ASP-009–010; [Destiny Fragment](/prd/destiny-fragment/) DO-FRG-009–010; [Destiny Ability](/prd/destiny-ability/) DO-ABL-005–010 |
| **Weapons Set** | All three weapon slots filled (Weapon Set and/or overrides) |
| **Armor + Mods Sets** | All five armor slots filled; Mod Set path present for combat mods |
| **General** | Exactly one of six artifacts selected; **artifact perks/config filled out** (not empty config) |
| **Fashion** | Optional — not required for composition complete |

| ID | Rule |
| --- | --- |
| DBR-CMPL-001 | Default must meet the full combat loadout checklist above to save as default. |
| DBR-CMPL-001a | Artifact selection alone is not enough. Artifact **perk/config** must be complete for default. |
| DBR-CMPL-001b | Fashion is optional on default. |
| DBR-CMPL-001c | Class and subclass **tree** come from the Build (shared). Variant supplies kit choices in Subclass area. |

### 3.3 Three gates (default)

| Order | Gate | Blocks |
| --- | --- | --- |
| 1 | **Compose complete** | Default save if checklist §3.2 fails |
| 2 | **Required links** | Default save if required synergy Objects lack equip-ready pins (DBR-SYN-010a) |
| 3 | **Equip-ready** | Equip and DIM export if any applied combat slot lacks a non-stale pin |

Wishlist identity may exist under gate 1. Gates 2 and 3 still need pins.

| ID | Rule |
| --- | --- |
| BR-VAR-050 | Default save requires gate 1 and gate 2. |
| BR-VAR-051 | Equip and DIM export require gate 3 (and practical gate 1 for a coherent loadout). |
| BR-VAR-052 | Non-default save does not require gate 1 full checklist or gate 2; soft guidance only for coverage. |

## 3a. Constraints (hard vs soft)

### Hard on variant save

| Constraint | Applies | Rule |
| --- | --- | --- |
| **Default full loadout** | Default | Checklist §3.2 (incl. artifact perks filled) |
| **Illegal subclass kit** | Any | Invalid aspect/fragment/ability kit cannot save |
| **Dual exotic** | Any | At most one exotic weapon and one exotic armor (incl. exotic class item) on resolved loadout |
| **Slot conflict** | Any | Two attached Sets cannot claim the same equipment slot |
| **Set attach rules** | Any | Attach only Sets that pass Set save rules; one live Set per type ([Domain Set](/prd/domain-set/)) |
| **Pair armor match** | Any | Pair exotic armor must match build exotic armor when set |
| **Exotic ability pin** | Any | When exotic requires an ability, mismatch blocks save after confirm path (DBR-SUB-005) |
| **Required synergy links** | **Default only** | Required links hard-check on default; satisfaction = pins only (DBR-SYN-010a) |

### Hard on equip / export

| Constraint | Rule |
| --- | --- |
| **Equip-ready** | Every applied combat slot needs a non-stale owned pin |
| **Stale pin** | Missing instance after sync → mark stale; block equip until re-pin |
| **Equip with gaps** | Non-default only; empty slots leave character gear; **user confirm** required |

### Soft only

| Topic | Rule |
| --- | --- |
| Empty combat slots | Allowed on **non-default** save |
| Weak synergy coverage | Soft on non-default; does not block save |
| Soft stat targets below threshold | Warning only |
| Weapon element vs subclass | Soft / synergy-based |
| Catalyst / deepsight | Display only |
| Activity-gated mods | May save with warn |

### Build-owned (not decided here)

| Topic | Owner |
| --- | --- |
| Designated synergy Types, ≥1 Type | [Domain Build](/prd/domain-build/) |
| Exotic armor item identity, build-shared exotic weapon, build-pinned Super | [Domain Build](/prd/domain-build/) |
| Confirm in-place vs fork on identity change | [Domain Build](/prd/domain-build/) |
| Class and subclass **tree** shared | [Domain Build](/prd/domain-build/) / DBR-SUB-001 |

## 4. In scope / out of scope

**In**

- Four fixed areas on every variant (General, Subclass, Armor + Mods, Weapons)
- Add, rename, switch, compare, delete variants (delete/default rules below)
- Default vs non-default completeness
- Set operations in Sets areas: **Create**, **Edit**, and **Attach** kept distinct
- Create/Edit use shared Sets lifecycle; Attach is a separate flow
- Slot overrides in the correct area
- Wishlist rolls vs pins; equip-ready gate
- Artifact and fashion under General
- Soft guidance and soft stats
- Destiny hard loadout constraints on the resolved kit

**Out**

- Editing Build identity without Build confirm/fork flow
- Treating concept tags as identity
- Soft misses as hard blocks on non-default save
- Merging or omitting any of the four areas
- Merging Create/Edit/Attach into one overloaded Sets control
- Lite or forked Set create/edit chrome inside the variant
- Owning library Set body rules (opens [Area Sets](/prd/area-sets/) / [Domain Set](/prd/domain-set/))
- Owning library Synergy CRUD UI (opens [Area Synergy](/prd/area-synergy/))

## 5. Success

| Signal | Pass when |
| --- | --- |
| Four areas | Every variant shows General, Subclass, Armor + Mods, Weapons |
| Distinct Set ops | Create/Edit match Sets lifecycle; Attach is separate |
| Default complete | Default saves only as full combat loadout |
| Non-default gaps | Non-default may save with empty combat slots |
| Compose | Resolved loadout has no slot conflicts |
| Wishlist vs equip | Save without pins OK; equip/export blocked until equip-ready |
| Artifact / fashion | Differ per variant under General; equip applies them |
| Soft guidance | Coverage visible; non-default save not blocked by soft |
